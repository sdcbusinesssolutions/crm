# Admin Impersonation Feature (Login as User) - Technical Deep Dive

This document provides a comprehensive, end-to-end explanation of the **"Login as User"** feature. It covers the user experience flow, the exact API mechanisms used for token generation, and the security architecture.

---

## 1. The User Experience (UX) Flow

### Scenario: Admin wants to debug "John Doe's" account.

#### A. The Entry Point: Admin Users List
1.  **View**: The Admin logs in and navigates to the **Users** page (`/admin/users`).
2.  **Interface**: The admin sees a table listing all users involved in the system.
    *   *Columns*: User Details (Name/Email), Status, Contact, Plan, Actions.
3.  **Action**: The Admin finds "John Doe" (john@example.com) and hovers over the row.
4.  **Trigger**: The Admin clicks the **"Login"** button in the *Actions* column.

#### B. The Process (Invisible to User)
1.  **Feedback**: A toast notification appears: *"Impersonating... Generating login link for John Doe..."*.
2.  **API Call**: The frontend sends a secure request to the backend.
3.  **Success**: The backend returns a special URL.

#### C. The Transition
1.  **Browser Behavior**: A **New Tab** opens automatically.
2.  **Redirection**: The browser loads the Supabase Verification URL, which instantly validates the token.
3.  **Landing**: The browser redirects to the Client Portal (`http://localhost:3000`).

#### D. The Impersonation State
3.  **Visual Cue**: The Admin (now logged in as John) sees the **Client Portal Dashboard**.
    *   This is the exact same view the user sees: Stats, Flows, Inbox, Contacts, etc.
    *   This allows the Admin to verify exactly what the user is experiencing.
4.  **Safety Banner**: A **RED BANNER** is fixed at the top of the screen:
    > **⚠️ You are impersonating this user. [BACK TO ADMIN]**
5.  **Persistence**: If the Admin refreshes the page, the banner remains.

#### E. The Exit (Logout)
1.  **Action**: The Admin clicks the **"BACK TO ADMIN"** button on the red banner.
2.  **Result**:
    *   The "John Doe" session is destroyed (Logged out).
    *   The browser redirects back to the Admin Panel User List (`/admin/users`).

## 2. Technical Architecture & Data Flow

### Step 1: Frontend Request (`Users.tsx`)
When the button is clicked, the `handleAction` function triggers:

```typescript
// client/src/pages/admin/users/Users.tsx

const handleAction = async (action: string, user: any) => {
    if (action === 'Login') {
        const token = localStorage.getItem('adminToken'); // Get Admin's JWT
        
        // 1. Call Backend API
        const res = await fetch('http://localhost:5000/api/admin/users/login-as', {
            method: 'POST',
            headers: { 
                'Authorization': `Bearer ${token}`, // Proof of Admin Status
                'Content-Type': 'application/json'
            },
            body: JSON.stringify({ email: user.email }) // Target User
        });

        // 2. Handle Response
        if (res.ok) {
            const data = await res.json();
            // 3. Open Magic Link in New Tab
            window.open(data.url, '_blank'); 
        }
    }
};
```

### Step 2: Backend Token Generation (`UsersController.js`)
This is the core of the security logic. We use the **Supabase Service Key** to bypass normal authentication rules.

```javascript
// server/controllers/admin/UsersController.js

exports.impersonateUser = async (req, res) => {
    const { email } = req.body;

    // 1. Use the Admin Client (initialized with SERVICE_ROLE key)
    // This key has "God Mode" privileges.
    const { data, error } = await supabaseAdmin.auth.admin.generateLink({
        type: 'magiclink',      // Request a one-time login link
        email: email,           // For this specific user
        options: {
            // CRITICAL: Tell Supabase where to send the user after verification.
            // We append '?impersonated=true' so the Frontend knows to show the banner.
            redirectTo: `${process.env.CLIENT_URL}/?impersonated=true`
        }
    });

    // 2. Return the Action Link
    // content of data.properties.action_link looks like:
    // https://project.supabase.co/auth/v1/verify?token=xyz...&type=magiclink&redirect_to=...
    res.json({ url: data.properties.action_link });
};
```

### Step 3: The Magic Link Explained
The URL generated by Supabase contains everything needed to securely create a session.

**Example URL:**
`https://<YOUR_PROJECT_ID>.supabase.co/auth/v1/verify?token=4a5b6c...&type=magiclink&redirect_to=${process.env.CLIENT_URL}/?impersonated=true`

*   **`https://.../verify`**: The Supabase Auth server endpoint.
*   **`token=4a5b6c...`**: A one-time, cryptographically secure token. When the browser hits this, Supabase validates it.
*   **`type=magiclink`**: Tells Supabase this is a passwordless login attempt.
*   **`redirect_to=...`**: The final destination. Supabase will append access tokens (Hash fragment) to this URL.

### Step 4: Client Session Initialization (`App.tsx`)
When the browser follows the `redirect_to` link, it lands on `http://localhost:3000`.

1.  **Supabase Client (`supabase.auth.getSession`)**: Detects the `#access_token=...` in the URL hash.
2.  **Session Creation**: It automatically exchanges this hash for a valid Session object (User User, JWT Token, Refresh Token) and saves it to LocalStorage.
3.  **App State**: The `MainApp` component sees `session` is true and renders the Dashboard.

### Step 5: Banner Logic (`ImpersonationBanner.tsx`)
How do we know to show the red banner?

```typescript
// client/src/components/ImpersonationBanner.tsx

useEffect(() => {
    // 1. Check URL for flag from Step 2
    const params = new URLSearchParams(window.location.search);
    if (params.get('impersonated') === 'true') {
        // 2. Set "Persistent" Flag in Session Storage
        sessionStorage.setItem('is_impersonating', 'true');
        setIsImpersonating(true);
    } 
    // 3. Check Session Storage (for page reloads)
    else if (sessionStorage.getItem('is_impersonating') === 'true') {
        setIsImpersonating(true);
    }
}, []);
```

### Step 6: The "Back to Admin" Flow
When the admin is done:

```typescript
const stopImpersonation = async () => {
    // 1. Kill the Client Session
    await supabase.auth.signOut(); 
    
    // 2. Clear the Impersonation Flag
    sessionStorage.removeItem('is_impersonating');
    
    // 3. Send back to Admin Panel
    window.location.href = '/admin/users';
};
```

## 3. User Status Management (Block/Unblock)

In addition to impersonation, Admins can now manage user access directly from the table.

### A. Blocking a User
1.  **Action**: Click the **"Block"** button (Amber) next to an Active user.
2.  **Backend Logic**: Sets the user's `banned_until` property in Supabase to a distant future date (approx. 100 years).
3.  **Result**:
    *   The user's status changes to **"Inactive"** (Red).
    *   **Login Prevention**: The user cannot log in to the Client Portal.
    *   **Impersonation Prevention**: Typically, generating a magic link for a banned user will result in a restricted session or correct "User is banned" error from Supabase.

### B. Unblocking a User
1.  **Action**: Click the **"Unblock"** button (Green) next to an Inactive/Banned user.
2.  **Backend Logic**: Removes the `banned_until` property (sets to null).
3.  **Result**: The user's status reverts to **"Active"** (Green), restoring access.

### C. API Endpoint
*   **Route**: `POST /api/admin/users/status-toggle`
*   **Body**: `{ "userId": "...", "action": "activate" | "deactivate" }`

## 4. Security Considerations

1.  **Service Role Key**: The backend uses the `SUPABASE_SERVICE_KEY`. This key **MUST NEVER** be exposed to the client. It is kept in `server/.env`.
2.  **Admin Authorization**: The `/login-as` and `/status-toggle` endpoints are protected by `verifyAdminToken`. Only an authorized admin can perform these actions.
3.  **One-Time Token**: The magic link token is single-use. Once clicked, it cannot be reused.
4.  **Audit Trail**: It is highly recommended to add a database log in `UsersController.js` just before generating the link:
    *   `INSERT INTO admin_audit_logs (admin_id, action, target_user) VALUES (...)`
